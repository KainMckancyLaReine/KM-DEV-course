Setup

Connecting the backend.

Five steps, about ten minutes. Until they are done the academy runs in preview mode, which uses the same interface against a store in this browser.

What preview mode is

Every screen, every interaction and every piece of course content is real. What is not real is the account: sign-ups, sessions and progress live in localStorage in the browser you are using, and they are gone if you clear it. There is no server, so there is nothing to protect and nothing to trust.

It exists so the whole product can be walked through and judged before any infrastructure is set up — not as a substitute for one. The banner says so on every page, because a login screen that only pretends to be a login screen is worse than no login screen.

What changes when you connect it

Accountsreal, hashed by Supabase
Sessionsrefreshed, survive a restart
Password resetby email
ProgressPostgres, any device
Authorizationrow level security
Quiz gradingserver-side function

Not one line of the interface changes. The data layer has two adapters behind one API, and the config file decides which one runs.

01 — Create the project

Make a new project at supabase.com. The free tier is enough for this. Then open Settings → API and copy the Project URL and the anon public key.

The anon key is meant to be public — it identifies the project, it does not grant access. Access is decided by the policies you install in the next step. Never put the service role key anywhere near this repository.

02 — Install the schema

In the SQL editor, run db/schema.sql and then db/seed.sql. The first creates the tables, the row level security policies, the grading function and the admin bootstrap table. The second fills in the course.

Both are generated and committed, so a fresh environment is always one copy-paste away from being identical to yours.

03 — Point the front end at it

Open assets/js/km-config.js and paste the two values in:

assets/js/km-config.js
1window.KM_CONFIG = {
2 supabaseUrl: 'https://YOUR-PROJECT.supabase.co',
3 supabaseAnonKey: 'YOUR-ANON-KEY',
4 courseSlug: 'ai-web-developer'
5};

Commit it. The preview banner disappears on the next load and every screen is talking to Postgres.

04 — Create the two accounts

Go to /signup.html and create them normally:

  • Kain — kain@km.dev. This address is in the admin_bootstrap table that seed.sql installs, so the trigger that creates the profile marks it as an admin at the moment of sign-up.
  • User B — userb@km.dev. An ordinary student account, so you can see exactly what a student sees.

You choose both passwords in the browser. They are hashed by Supabase and never appear in this repository — which is why there is no password written down anywhere in it, including here.

To add another admin later, either add the address to admin_bootstrap before they sign up, or update their role in the profiles table. A student cannot change their own role: a trigger rejects it.

05 — Check it refuses what it should

Worth doing once, because it is the part nobody tests. Sign in as User B, open the browser console and ask for something a student should not have:

console
1// as a student — returns only their own row
2await KMDB.admin.users() // throws: forbidden
3// the correct answers to a quiz are not selectable at all

Both refusals come from the database, not from the interface. That is the difference between hiding a button and having a permission.

Everything else

The course itself is version-controlled.

Levels, lessons, assessments, projects and prompts all live in content/*.json. Run build/gen_seed.py and both the SQL seed and the browser copy are regenerated from it.
